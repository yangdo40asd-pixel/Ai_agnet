# 사용자 경험 중심 재설계 — 현행 진단과 실행 계획

작성일: 2026-10-28  
범위: 사용자 제공 지시서의 PHASE 0. 실제 구현에 착수하기 전 확인한 내용과 계획이다.

## 1. 방향과 이번 진단의 범위

목표는 사용자가 테마나 기업을 자유롭게 묻고, 답변에서 핵심을 이해한 다음 추가 질문을 이어갈 수 있는 금융 대화 서비스다. 채팅은 설명의 중심이고, 캔버스는 표·차트·상세 근거가 필요할 때 확인하는 공간이다. 모든 질문을 같은 형식이나 같은 길이로 출력하는 것이 목적이 아니다.

사용자가 전달한 사용자 흐름 설계와 지시서, 기존 화면 이미지, 현재 코드와 기존 검수 기록을 대조했다. 실제 열린 브라우저 화면 접근은 승인 게이트에서 거절되어 이번에는 직접 확인하지 못했다. 따라서 화면에 대한 관찰은 사용자가 제공한 이미지 기준이다. 최초 문서 작성 시에는 실행 검수를 수행하지 않았으나, 후속 지시에 따라 아래 8절에서 실제 프로그램 함수·외부 자료 수집·로컬 모델·전체 회귀 검사를 수행했다. 기존 브라우저 세션을 읽지 않고 독립된 진단 프로세스에서 검수했다.

저장소는 `D:\ai_agent`, 브랜치 `woong`, HEAD `4a197cb`이며 기존 미커밋 변경이 다수 있다. 기존 변경을 폐기하거나 커밋·푸시하지 않는다. 이번 후속 검수에서도 현재 코드의 자동 검사 716개가 50.611초에 통과했다. 과거 기록과 이번 결과는 별도 증거로 보존한다.

## 2. 현재 실제 처리 흐름

1. `src/ui/app.py`의 `process_chat_message` / `_process_chat_message`가 입력과 첨부를 받아 `src/ui/chat_lifecycle.py`의 `start_request`로 질문 원문·대화 기록·요청 ID를 보존한다.
2. `src/agents/request.py`의 `route_message`가 문장, 후보 종목, 선택 종목, 이전 대화를 바탕으로 테마 탐색·종목 선택·조회·대화·비교 등으로 분기한다. 일부는 정규식, 그 밖에는 모델 분류를 사용한다.
3. 테마 탐색은 `src/pipeline.py`의 `discover_theme_candidates`가 `src/agents/report.py`의 `propose_candidates`로 이름을 제안받고 `src/data/stock.py`의 `resolve_candidates`로 상장 여부와 종목코드를 확인한다. 여기서 상장 확인은 해당 테마의 사업 관련성을 입증하지 않는다.
4. 선택 또는 특정 종목 요청은 `src/ui/app.py`의 `analyze_pending_selection`에서 `src/pipeline.py`의 `analyze_selected_stock`으로 이어진다. 요청 범위와 설정에 따라 가격·차트, OpenDART 재무자료, 뉴스, AI 설명 등을 수집한다. `src/analysis_flow.py`의 `needs_data`가 기존 자료 재사용 여부도 판단한다.
5. **원래 사용자 질문이 있는 종목 요청**은 수집 후 `_answer` → `src/agents/chat.py`의 `answer_question`으로 넘겨 질문에 맞춘 답을 생성한다. **종목 버튼 선택 등 질문이 없는 경우**는 `src/analysis_flow.py`의 `analysis_response`가 실적 수치와 기존 AI 설명을 정해진 블록으로 조립한다. 두 진입 방식의 결과 경험은 다를 수 있다.
6. 대화 답변은 `src/agents/evidence.py`, `answer_quality.py` 등에서 관련 근거를 고르고, `chat.py`에서 모델 생성 및 숫자·근거·의미 검사를 거친다. 일부 검증 실패는 한 차례 피드백 후 재생성하고, 다시 실패하면 제한된 사실 기반 대체 응답으로 돌아갈 수 있다.
7. `src/ui/answer.py`가 답변과 출처를 표시하고 `src/ui/app.py`의 `render_conversation`이 후보 선택·상세 버튼을 붙인다. 결과는 `src/ui/state.py`의 `result_id`로 보관한다. 사용자가 상세 버튼을 누르면 `add_canvas` → `render_canvases` → `src/ui/dashboard.py`의 시각 자료 및 `src/export/excel.py`의 출력으로 이어진다.
8. 두 종목 비교는 별도 `src/comparison_flow.py` 경로다. 현재 지원하는 비교는 연간 매출·영업이익·영업이익률 중심이며 PER·분기·뉴스 등은 같은 경로에서 지원하지 않는다.

## 3. 확인된 문제와 미확정 원인

이 절은 최초 정적 진단이다. 이후 실제 재현으로 확정·보완된 내용은 8절을 우선한다.

### 3.1 테마 탐색이 세 종목 선택에 머무름 — 코드로 확인

- 사용자 화면에서 세 기업 이름과 선택 버튼, 후보 상세 표, 별도 선택 목록이 함께 나타난다.
- `src/agents/report.py:16`은 서로 다른 세 종목을 모델에 요구하고, `src/data/stock.py:20`은 정확히 세 개가 아니면 오류로 처리한다. 따라서 단순 표시 제한이 아니라 생성·검증 계약도 세 개에 묶여 있다.
- `src/ui/app.py:372`부터는 확인된 이름과 상장 확인 안내를 보여 준다. 현재 이 경로에서 기업별 사업 차이나 확인된 테마 연관 근거를 설명하지 않는다.
- `src/ui/app.py:698`부터 선택 버튼, 상세 표와 선택 목록, 선택 안내가 같은 위치에 중복 배치된다. 화면의 `not_collected` 같은 내부 상태도 사용자에게 의미가 불분명하다.
- 단순히 세 개를 열 개로 늘리면 관련성 검증, 중복 방지, 속도 문제가 생긴다. 사업 관련 근거의 확보 가능 범위부터 확인해야 한다.

### 3.2 종합 질문이 수치만으로 끝난 경험 — 현상 확인, 실행 원인 미확정

- 사용자는 “삼성SDI는 어때?”에 대해 현재가와 PER만 받은 사례를 제공했다. 이 답변은 당시 질문의 넓은 의도에 비해 정보가 부족하다. 제공된 수치가 현재의 실제 시세를 의미하는 것은 아니다.
- `src/ui/app.py:448`은 `limited_on_failure=True`를 사용하고, `src/agents/chat.py:504`의 `_verified_fallback`은 검증된 문장이나 현재가·PER 등을 모아 제한 답변을 만든다. `chat.py:710` 이후 검증 실패 재시도 뒤 이 경로가 사용될 수 있고, 화면 문장 형태도 일치한다.
- **하지만 해당 실행의 요청·검증 로그는 이번에 확인하지 못했다.** 그 답변이 실제로 이 경로에서 나왔는지, 어떤 검증이 실패했는지, 재무자료가 충분했는지 확정하지 않는다. 최초 질문 라우팅·자료 수집 범위와 재시도 사유를 함께 재현해야 한다.
- `src/agents/request.py:228`은 이전 메시지의 지표 표현에 따라 일부 평가 질문 범위를 `finance`로 좁히기도 한다. 어떤 대화에서 유익하고 어떤 대화에서 종합 의도를 잃는지는 반례와 함께 확인해야 한다.

### 3.3 종목 선택 후 숫자 위주의 고정 요약 — 코드로 확인

`src/analysis_flow.py:62`의 `analysis_response`는 비교 가능한 연간 수치를 ‘연간 실적’ 블록으로 나열하고 뉴스·재무 설명 블록을 추가한다. 이는 확보된 정보를 전달하지만, 선택 당시 사용자가 원한 평가와 의미 설명을 반드시 만족시키는 구조는 아니다. 직접 질문 경로와 버튼 선택 경로의 답변 품질을 따로 검수하고, 공통 데이터·검증을 재사용하면서 첫 답변의 목적을 일관되게 설계해야 한다.

### 3.4 뉴스의 실질적 설명 부족 — 화면 현상 확인, 원인 추가 조사

사용자가 제공한 화면은 ‘계획이 보도되었습니다’ 수준의 짧은 문장, 반복된 ‘테마 동향’, 하이픈이 길게 보이는 부분을 보여 준다. 사건·기업·의미를 이해하기 어려운 것은 확인되나, 하이픈의 발생 위치나 원문·생성·정규화·렌더링 중 어느 단계의 문제인지는 아직 불명이다. `src/agents/report.py`의 설명 생성, `src/agents/news_relevance.py`의 기사 선별, `src/agents/issues.py`의 사건 묶기, `src/ui/answer.py`의 렌더링을 실제 입력과 출력으로 단계별 비교한다. 뉴스 제목·검색 발췌만 확보했다면 기사 본문을 읽은 것처럼 설명하지 않는다.

### 3.5 자유로운 질문의 범위 제한 — 코드로 확인

- `src/agents/request.py:176`은 일부 최근 인기·순위 질문을 미지원으로 안내한다. 최신 인기 테마를 정확히 제공하려면 실제 최근 시장 자료와 선정 기준이 필요하다.
- `src/comparison_flow.py:10`은 현재 두 기업의 연간 일부 항목 비교만 지원하며 PER 등은 명시적으로 제한한다. 사용자 흐름의 다수 기업 비교·동종 PER 비교는 목표이지 현재 구현 완료가 아니다.
- 같은 파일의 `comparison_followup`은 제한된 문형만 받는다. 자유로운 후속 질문의 실제 성공 범위는 연속 대화 검수로 확인한다.
- 과거 검수 문서에도 어닝콜 원문, 컨센서스, 같은 기준 동종 PER 등의 수집은 미완료로 기록돼 있다. 자료가 없으면 만들어내지 않는다.

### 3.6 중복 답변과 속도 — 조사 필요

`src/ui/app.py:414` 부근 오류 처리에는 채팅 메시지 추가와 `st.error` 표시가 함께 있어 오류가 두 위치에 노출될 가능성이 있다. 이는 사용자가 보고한 특정 중복의 원인으로 확정된 것은 아니다. 정상 답변 중복, rerun, 재시도도 별도로 재현해야 한다.

`src/pipeline.py`는 가격·차트·DART·뉴스·설명 일부의 `timings_ms`를 기록한다. 수집 뒤 원래 질문 답변까지 별도로 생성할 수 있지만 실제 병목이라는 뜻은 아니다. 기존 기록의 한 사례는 총 89.625초 중 로컬 생성·심사 14.438초이며 나머지 약 75초의 세부 원인은 확정되지 않았다. 사용자 사례의 약 66초 역시 구간별 로그 없이 원인을 단정할 수 없다. 단계별 호출 횟수와 시간 기록의 누락을 확인하고 실제 실행에서 측정한다.

## 4. UI 변경안: 보존·통합·이동

| 요소 | 현 상태 및 계획 |
|---|---|
| 질문 입력·대화 | 유지하고 화면의 중심으로 둔다. 자유 입력이 항상 가능하다는 점을 분명하게 한다. |
| 종목 버튼·목록 | 같은 역할의 버튼과 선택 목록은 하나의 선택 방식으로 통합한다. 기업별 설명이 있으면 선택 목록에 간단히 연결한다. |
| 후보 상세 표 | 내부 상태값은 숨기거나 사람이 이해할 수 있는 말로 바꾼다. 코드·시장 등 세부 정보는 필요할 때 펼친다. |
| 반복 안내·박스 | ‘분석할 종목 선택’처럼 이미 조작 요소가 알려 주는 문구는 중복 여부를 검토한다. 답변 블록은 비교가 필요한 경우에만 강조한다. |
| 출처 | 채팅에는 읽기 쉬운 간결한 출처를 유지하고 세부 기준·조회 시각은 펼침 영역으로 둔다. 근거 연결은 삭제하지 않는다. |
| 후속 질문 | 맥락에 맞을 때만 선택적으로 제시한다. 동일한 내용을 직접 입력해도 처리되도록 한다. |
| 캔버스·Excel | 상세 버튼과 기존 결과 연결을 보존한다. 일반 대화에는 자동으로 열지 않고, 차트·표 요청 시 열기 방식은 실제 현재 지원 경로를 검증하며 구현한다. Excel도 유지한다. |
| 현재 대상·기록 | 현재 테마·종목을 간결히 표시한다. 주제 변경은 기존 대화 삭제와 분리하고, 새 대화에서만 문맥 초기화를 설계한다. 현재 저장·복원 범위는 추가 확인한다. |

화면 상태 예: 첫 화면은 질문 입력과 선택적 예시 → 테마 응답은 짧은 설명과 관련 기업 탐색 → 종목 질문은 핵심 판단·근거 → 추가 질문은 문맥 유지 → 상세 요청 시 해당 결과와 연결된 캔버스. 자료 부족·오류가 있으면 해당 부분만 간결하게 설명한다.

## 5. 수정 대상과 책임 분리

- `src/agents/request.py`: 종합 질문·지표 조회·테마 확장·비교의 의도와 참조 대상을 구분한다. 여러 기업의 역할을 무조건 단일 대상으로 합치지 않는다.
- `src/ui/chat_lifecycle.py`, `src/ui/state.py`: 질문 원문·요청 ID·결과 ID를 유지하며 대화 문맥과 화면/결과 상태의 경계를 점검한다. 새 주제와 새 채팅의 차이를 명시적으로 검수한다.
- `src/pipeline.py`, `src/analysis_flow.py`: 질문에 필요한 수집 범위와 재사용을 확인한다. 선택 시 요약과 자연어 질문의 답변 목적을 정리한다. 기존 `AnalysisResult`와 결과 연결은 보존한다.
- `src/agents/report.py`, `src/data/stock.py`: 세 종목 계약의 영향 범위와 확장 방법을 먼저 조사한다. 상장 검증과 사업 관련성 근거는 별도 책임으로 둔다.
- `src/agents/chat.py`, `src/agents/answer_quality.py`, `src/agents/evidence.py`: 질문에 필요한 근거 선택과 의미 설명을 개선하고, 제한 응답에 이른 이유는 진단 정보로 구분한다. 검증을 제거하거나 실패를 숨겨 정상 답변처럼 취급하지 않는다.
- `src/agents/news_relevance.py`, `src/agents/issues.py`, 뉴스 수집 영역: 근거 범위를 지키는 사건 요약과 중복 사건 묶기를 검증한다.
- `src/comparison_flow.py`, `src/data/company_comparison.py`: 동일 기간·연결/별도 기준을 지키는 기존 비교를 보호한다. 추가 비교는 데이터 가능성 확인 후 별도 범위로 추진한다.
- `src/ui/app.py`, `src/ui/answer.py`, `src/ui/dashboard.py`: 중복 컨트롤과 정보 위계를 정리하되 캔버스·출처·차트·Excel 연결을 유지한다.
- `src/agents/transport.py`, 공급자 모듈과 진단 기록: Local/Groq 분리를 유지하고 단계별 시간·재시도·실패 원인을 추적한다. 개인 키나 원문 민감 정보는 로그에 노출하지 않는다.

## 8. 후속 지시에 따른 실제 코드 실행 검수

### 8.1 방법과 경계

사용자가 요청한 것은 사용자 흐름을 기준으로 실제 프로그램을 판단해 보고하는 일이다. 이를 위해 프로젝트의 `route_message`, `discover_theme_candidates`, `analyze_selected_stock`, `answer_question`, `analysis_response`, 상태 관리 함수를 독립 진단 프로세스에서 호출했다. 실제 설정의 local 공급자와 기존 금융·뉴스 수집을 사용했다. 단순히 가상 수치를 모델에 직접 물었던 앞선 HTTP 시험과 다르다.

기존 브라우저 세션이나 페이지는 읽지 않았고, Streamlit 화면 렌더링도 이번 실제 호출 시험에 포함하지 않았다. UI 조건은 코드와 기존 사용자 이미지로 확인했다. 라우팅 확인은 실제 테마 후보·상장 목록과 명시적으로 구성한 대화 상태를 넣은 개별 사례다. 실제 답변은 삼성SDI 조회 후 “삼성SDI는 어때?” → “왜 그런 거야?” 순으로 이전 반환 문장을 이어 넣었다. 모든 목표 흐름을 한 세션에서 완주한 시험으로 해석하지 않는다.

- 자동 검사: 716개 / 50.611초 / OK. 실제 네트워크를 막은 기존 검사 도구를 사용했다.
- 실제 local 호출: 11회, 모두 공급자 함수가 반환했다. 업무 검증 통과와 HTTP/모델 반환은 다르다.
- 호출·시간 예산: 최대 20회·300초, 예산 초과 없이 종료. Groq 사용 없음. 서버 재시작·모델·환경설정 변경 없음.
- 실제 테마 후보: LG에너지솔루션, 삼성SDI, 에코프로비엠. 이번 조회의 상장 목록 2,871행. 이 이름과 수를 고정 정답으로 취급하지 않는다.
- 수집된 금융 수치는 해당 제공자가 반환한 표본이다. 수치의 최신성·공식 공시 원문과의 독립 대조까지 완료했다고 주장하지 않는다.
- 실행 원문과 오류·시간·상태, 진단 스크립트, 코드 해시는 [실행 증거 폴더](사용자경험_PHASE0_2026-10-28/)에 보관한다. 비밀 키 값은 기록하지 않았다.

### 8.3 삼성SDI 숫자만 출력되는 원인: 이번에는 확인됨

재현된 실행 순서는 다음과 같다.

1. 질문 라우팅은 `select/all`이었다. 따라서 이번 사례를 “라우터가 무조건 PER 질문으로 해석했다”로 설명하면 틀리다.
2. 금융·주가 이력·DART·뉴스 상태는 모두 `ok`였다. 연간 요약 3개와 뉴스 10개가 확보됐고, 분기 자료는 이 요청에서 별도 수집하지 않았다.
3. 기본 리포트는 `report_format`으로 두 번 실패했다. `src/agents/report.py:109`의 `_statement`는 `text`, `news_ids` 두 필드만 있는 객체를 요구하며, 실패 메시지는 “AI 설명의 근거 형식을 확인하지 못했습니다.”였다. 실제 모델 원문 전체는 이번 계측에서 보관하지 않아 어떤 필드가 어긋났는지는 확정할 수 없다.
4. 자료를 보존한 뒤 `answer_question`이 원래 질문으로 새 대화 답변을 생성했다. 두 차례 모두 `chat_numbers`의 “본문 수치는 확인된 값 자리표시자로 표시해야 합니다.”로 거절됐다. 해당 오류가 발생한 정확한 숫자·문장은 이번 원문 기록에 없어 정상 숫자 오탐인지 실제 잘못된 숫자인지는 후속 저장 재현으로 판별해야 한다.
5. `limited_on_failure=True` 경로가 `_verified_fallback`을 사용했고, 실제 반환 근거에 `answer_origin=verified_fallback`이 기록됐다.
6. 최종 반환은 **“확인된 현재가 534,000.00원, PER 875.41배입니다.”**였다. 사용자가 보고한 문장이 실제로 재현됐다. 이 수치만으로 기업의 현재 상황이나 가치평가를 판단한 것이 아니다.

대체 응답에서 재무 설명이 사라지는 구조도 확인했다. `chat.py:685` 부근의 검증 예시 문장 전달은 특정 비교 표현 조건 또는 분기·재요약 선택에 의존한다. `_verified_fallback`은 예시 문장이 없다면 이미 있는 연간 비교 사실을 직접 설명하지 않고 가격·PER로 내려갈 수 있다. 실제 재무자료가 존재하는데도 최종 답변에서 빠지는 문제다.

또한 “어때?”는 `request.is_evaluation_question`과 `chat.JUDGMENT_QUESTION`에서 모두 false로 확인됐다. 첫 라우팅이 성공했어도 뒤의 판단·대체 응답 정책에서 같은 의도가 일관되게 유지되지 않는다. 단어 하나를 전역 추가하는 방식은 지표 후속 질문을 종합 분석으로 확대할 수 있으므로, 질문 목적을 정한 결과를 이후 단계가 공유하도록 설계해야 한다.

AI 설명 처리에는 뉴스 관련성 판정 2회 약 5.87초와 기본 설명 호출 2회 약 58.83초가 포함됐다. 두 설명 호출은 모두 반환했지만 업무 형식 검사에서 실패했다. 수집과 추가 질문 답변을 합하면 약 81.5초이며, 실제 화면 업데이트 시간은 포함하지 않았다.

따라서 이번 사례의 핵심 병목은 외부 금융 API가 아니라 **실패한 기본 설명 처리 뒤 원래 질문의 답변을 다시 생성하는 구간**이었다. 이 결론을 모든 질문·모든 실행의 병목으로 일반화하지 않는다.

### 8.5 추가 코드 재현과 정상적으로 보존할 부분

- 가격만 있는 결과에서 “삼성SDI는 어때?”를 `needs_data`에 넣으면 DART 사용 가능 상태여도 추가 재무 수집이 false였다. 이는 실제 API 장애가 아니라 수집 조건의 재현이다. 가격 조회 뒤 종합 평가로 넘어갈 때 필요한 자료를 채우는 판단이 부족하다.
- `is_explicit_search('관련주 더 보여줘')`는 false였다. 기존 정규식에 추가 탐색 표현이 빠져 실제 모델 분류로 넘어갔다. 단순 숫자 제한뿐 아니라 탐색 의도와 이미 보여 준 기업을 관리할 계약이 없다.
- `follow_up_suggestions`는 ‘안녕하세요’와 일반 설명 대상만 넣어도 실적·PER·뉴스 질문 세 개를 고정 반환했다. 현재 `app.py`의 별도 `suggested_prompts` 경로는 상태에 따라 다르게 제안한다. 따라서 제안 로직이 두 군데 있고 호출 위치·실제 사용 여부를 정리해야 한다. 미사용 함수가 현재 화면에 고정 칩을 표시한다고 단정하지 않는다.
- 새 테마 저장 시 이전 채팅과 생성된 캔버스 결과 ID는 보존되고 선택 기업은 초기화됐다. 새 채팅 초기화는 메시지를 지웠다. 이 상태 관리 동작은 검수에서 정상 확인됐으므로 전면 교체할 이유가 없다.
- 기존 코드의 숫자·회사·기간·연결/별도 기준 검사, 저장 결과 및 Excel 경로는 재사용한다. 716개 검사는 기존 기능 보호에 유용하지만 이번 실패 흐름을 합격 기준으로 포함하지 않았다는 점을 분명히 해야 한다.

### 8.6 수정 계획의 구체화와 검증 방법

**우선 작업 1: 실패 원문과 목적별 계약을 고정한다(P0).**

- `report._statement`/`generate_commentary`, `chat.validate_answer`/`_check_answer`, 진단 계층에서 오류 코드와 거절된 문장·구조, 대상·기간, 생성·재작성·대체 응답 여부를 기록한다. 자격증명은 제외한다.
- 정상적인 숫자·근거 형식의 오탐과 실제 잘못된 숫자를 구분한 저장 회귀 사례를 만든다. 검사 제거·무조건 승인·실패 사례 삭제는 하지 않는다.
- 이번 실행의 수집 성공과 답변 설명 실패를 서로 다른 결과로 기록한다. 제한 답변을 분석 성공으로 집계하지 않는다.
- 검증: 정상 금융 숫자 표현·틀린 값·틀린 단위·다른 회사·다른 회계기간을 함께 대조한다.

**우선 작업 2: 질문 목적과 참조 대상을 공통으로 유지한다(P1).**

- `request.py`의 종합 평가/단순 지표/탐색 확장/비교/전망 목적을 수집과 근거 선택·대체 답변에 전달한다.
- `needs_data`에서 가격 조회 후 종합 질문에 필요한 재무·뉴스의 미수집 여부를 확인한다.
- “그 기업들”은 현재 후보 집합을 참조하고 “그중 삼성SDI”는 개별 기업으로 초점을 전환한다. 기준을 맞출 수 있는 비교 범위와 추가 데이터 개발 범위를 구별한다.
- 검증: ‘PER 얼마야 → 이 회사 어때?’, ‘그 회사 PER은 어때?’, ‘관련주 더 보여줘’, ‘그 기업들 비교’, ‘왜?’, 기업 전환을 정상·반례로 다룬다.

**우선 작업 3: 최초 답변과 제한 응답의 설명력을 맞춘다(P1).**

- 이미 확보한 연간 비교를 기준으로 종합 질문에 핵심 상황·필요한 근거·확인된 의미를 설명한다. 특정 회사나 긍정 결론을 하드코딩하지 않는다.
- 기존처럼 예시 문장이 없다는 이유만으로 연간 재무를 버리고 가격·PER만 보여 주는 동작을 바꾼다. 결정적 계산 기반 설명에도 관련 근거·결과 ID를 보존한다.
- 기본 리포트 생성이 원래 질문 응답에 실제로 필요한지 `pipeline`과 UI 호출 책임을 검토한다. 생성 결과를 재사용하거나 질문 맞춤 생성만 수행하는 최소 변경안을 비교하고, 버튼 선택의 기존 리포트·캔버스가 깨지지 않는지 검수한다.
- 검증: 이번 삼성SDI 재현과 재무 개선·혼재·결측·잘못된 근거 사례를 같은 경로에서 실행한다. 미래 사업 원인을 지어내지 않고 수치의 의미는 설명해야 한다.

**우선 작업 4: 화면과 상세 자료의 역할을 정리한다(P2).**

- 후보 선택 중복을 통합하고 사업 차이·관련 이유를 확보 가능한 근거로 연결한다.
- 차트 요청은 가격 기간·재무 기간·차트 종류를 구분한다. ‘최근 5년 매출’ 요청을 단지 주가 `5Y` 옵션으로 처리하지 않는다.
- 현재 대상과 보관된 캔버스 대상을 구별한다. 주제 전환 시 기록·캔버스 보존은 이번에 확인한 동작을 유지한다.
- 검증: 결과 ID별 표시·표·차트·Excel 및 실제 화면 육안 검수는 각기 별도로 수행한다.

**우선 작업 5: 측정된 호출을 줄인다(P3).**

- 이번 64.715초의 실패한 기본 설명을 중심으로 생성/재작성 횟수·필수 여부를 조정한다. 정상 답변의 검증은 유지한다.
- 검증: 같은 질문·같은 보관 자료로 변경 전후 호출 수와 지연·대체 응답 발생을 비교하고, 별도 실제 API 흐름도 확인한다. 호출 성공만으로 품질 성공을 선언하지 않는다.
