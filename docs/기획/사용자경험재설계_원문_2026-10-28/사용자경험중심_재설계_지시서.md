# AI 테마주 인사이트 리포트 — 사용자 경험 중심 재설계 지시서

**수신 대상:** 현재 프로젝트를 개발 중인 Codex  
**문서 목적:** 기존 개발 방향의 문제를 진단하고, 대화 UX·UI·데이터 처리·코드 구조를 사용자 경험 중심으로 재정렬한다.  
**개발 원칙:** 무분별한 기능 추가 금지 / 기존 기능 최대한 재사용 / 실제 사용자 대화 검증 우선

---

# 0. 가장 먼저 이해해야 할 사항

이번 요청은 기존 프로그램에 기능을 추가하거나, 답변 프롬프트를 조금 개선해 달라는 요청이 아니다.

우리는 개발 과정에서 여러 차례 답변 품질을 개선하고, 금융 수치 검증 규칙을 추가하고, 다양한 예상 질문 시나리오를 작성했다.

하지만 실제 프로그램을 사용해 본 결과, 사용자가 기대하는 **대화형 금융 챗봇의 경험**과 현재 프로그램 사이에 상당한 차이가 있었다.

지금 필요한 것은 기능 확장이 아니라 **제품의 사용자 경험을 중심으로 기존 구조를 재검토하는 작업**이다.

이번 재설계의 핵심 목표는 다음과 같다.

> 사용자가 관심 있는 금융 테마나 기업을 자유롭게 질문하면, AI가 문맥을 이해하고 필요한 자료를 확인한 뒤, 핵심 내용을 이해하기 쉽게 설명하며, 후속 질문까지 자연스럽게 이어가는 프로그램을 만든다.

데이터 조회, 수치 검증, 뉴스 수집, 차트, Excel, 캔버스는 모두 이 목표를 지원하는 수단이다.

**기능이 정상적으로 실행되는 것과 사용자의 궁금증이 해결되는 것은 다르다.**

이 차이를 기준으로 프로젝트를 다시 평가해야 한다.

# 1. 우리는 어디에서 막혔는가?

## 1.1 최초의 개발 목표

프로젝트는 테마주 검색, 종목별 금융 정보 조회, 기업 분석, 관련 뉴스 수집, 사용자와의 대화, 시각화 및 보고서 기능을 제공하는 AI 금융 챗봇을 목표로 개발되었다.

기존 구성에는 다음 기술과 데이터 소스가 포함되어 있다.

- Python 및 Streamlit 기반 사용자 인터페이스
- KRX 관련 테마·종목 데이터
- OpenDART 기반 기업 재무정보
- Yahoo Finance 기반 주가·가치평가 데이터
- NAVER 뉴스 기반 관련 기사
- Groq 또는 로컬 LLM을 이용한 답변 생성
- 상세 결과 캔버스 및 Excel 출력

실제 저장소에서 현재 적용 여부와 동작 상태를 먼저 확인할 것.

초기 목표는 여러 금융 자료를 AI가 활용하여 사용자가 이해하기 쉬운 기업 분석을 제공하는 것이었다.

그러나 개발이 진행되면서 **데이터를 가져오고 검증하는 기능의 완성도**가 점차 개발의 중심이 되었다.

## 1.2 첫 번째 문제: 테마 검색이 탐색 경험으로 이어지지 않음

실제 사용 예시:

**사용자:** 2차전지 관련 주 알려줘.

**프로그램:** LG에너지솔루션, 삼성SDI, 에코프로비엠 등 세 종목을 보여주고 선택하도록 안내.

문제는 세 기업이 표시된 것 자체가 아니다.

사용자는 다음 내용을 알기 어렵다.

- 왜 이 기업들이 2차전지 관련주인지
- 서로 어떤 사업적 차이가 있는지
- 이 밖에 어떤 관련 기업들이 있는지
- 배터리 제조사와 소재·장비 기업이 어떻게 구분되는지
- 다음에 무엇을 탐색할 수 있는지

결과적으로 **테마 탐색이 종목 선택 과정으로 축소되었다.**

사용자는 기업 목록을 받았지만, 테마 자체에 대한 이해를 얻지 못했다.

## 1.3 두 번째 문제: 사용자의 질문 의도가 지나치게 좁게 해석됨

실제 사용 예시:

**사용자:** 삼성SDI는 어때?

**프로그램:**

> 확인된 현재가 534,000.00원, PER 875.41배입니다.

응답에 약 1분이 소요되었음에도, 사용자는 삼성SDI의 현재 상황을 이해하기 어렵다.

앞선 문맥에서 사용자는 2차전지 관련주를 탐색했고, 그중 삼성SDI에 관심을 보였다.

따라서 이 질문에서 자연스러운 기대는 다음과 같다.

- 삼성SDI의 최근 사업·실적 상황은 어떤가?
- 좋은 흐름인가, 어려움을 겪고 있는가?
- 최근 주요 뉴스나 사업 변화는 무엇인가?
- 다른 2차전지 기업과 비교했을 때 특징은 무엇인가?

즉, 사용자는 **종목의 현재 상태에 대한 종합적인 평가**를 기대했다.

그러나 프로그램은 질문을 사실상 가격·PER 조회로 처리했다.

이는 수치 데이터가 부족한 문제만이 아니라 **문맥 기반 질문 해석과 답변 목표 설정의 문제**이다.

특히 PER이 875.41배처럼 매우 높게 표시된다면, 그 수치가 어떤 기준으로 계산되었는지와 이익 규모의 영향 등을 확인해 설명해야 한다.

단순히 숫자를 출력하거나, 반대로 숫자만 보고 고평가라고 단정해서는 안 된다.

## 1.4 세 번째 문제: 금융 분석이 수치 나열로 변질됨

다른 종목을 선택하면 매출액, 영업이익, 영업이익률, PER 등 여러 지표가 표시되기도 했다.

하지만 그 숫자가 **어떤 의미를 가지는지**가 충분히 설명되지 않았다.

예를 들어 매출 증가율과 영업이익 증가율이 제시되었다면 다음 질문에 답할 수 있어야 한다.

- 매출보다 영업이익이 더 빠르게 증가했는가?
- 수익성이 개선되었는가?
- 이 기업의 최근 상황을 긍정적으로 볼 근거가 있는가?
- 개선 또는 악화된 이유를 뒷받침하는 구체적인 자료가 있는가?

사용자가 숫자를 읽고 스스로 결론을 도출해야 한다면, 대화형 분석 서비스의 가치가 줄어든다.

**금융 데이터를 설명에 활용해야지, 금융 데이터 자체가 답변을 대체하게 해서는 안 된다.**

## 1.5 네 번째 문제: 뉴스가 실제 분석으로 연결되지 않음

뉴스 답변에서 다음과 같은 기계적인 표현이 발생했다.

> 계획이 보도되었습니다.

이 문장은 실제로 어떤 일이 있었는지, 기업에 무슨 의미가 있는지 알려주지 않는다.

좋은 뉴스 분석은 최소한 다음 관계를 설명해야 한다.

**무슨 사건이 발생했는가 → 어느 기업과 관련되는가 → 사업이나 실적에 어떤 의미가 있는가**

또한 서로 다른 기사 세 개를 가져왔다고 해서 반드시 사건 세 개가 되는 것은 아니다.

여러 기사가 동일한 실적 발표를 다룬다면 하나의 사건으로 정리해야 한다.

반대로 사용자가 산업 전반의 흐름을 물었다면 개별 사건만 나열하지 않고 산업의 중요한 변화를 설명할 수 있어야 한다.

## 1.6 다섯 번째 문제: 정상적인 후속 질문도 실패하거나 대화가 끊김

과거 실제 사용에서 다음 문제가 관찰되었다.

- "그럼 올해는 어떻고 내년은 어떨 것 같아?" 같은 후속 질문이 정상적으로 처리되지 않음
- 사실 근거나 질문 충족 여부를 확인하지 못했다는 안내만 출력됨
- 사용자에게 보여서는 안 되는 내부 지시성 문구가 노출됨
- 동일한 질문에 답변이 중복 표시된 사례가 있음
- 답변 생성에 수십 초에서 약 1분이 소요됨
- 오랜 대기 끝에 지나치게 짧거나 실질적인 정보가 부족한 답변이 나옴

이 현상들의 정확한 코드상 원인은 아직 확정하지 않았다.

따라서 프롬프트 문제, 검증기 문제, 데이터 조회 문제, 상태 관리 문제, 렌더링 문제를 구분해 조사해야 한다.

특히 현재 검증 체계가 정상적인 답변까지 거부하고 있는지 확인할 필요가 있다.

## 1.7 여섯 번째 문제: UI가 대화를 돕기보다 복잡하게 만듦

현재 화면에는 종목 선택 버튼, 상세 표, 다른 선택 영역, 상태 메시지, 후속 질문 등이 함께 나타날 수 있다.

사용자가 겪는 문제는 다음과 같다.

- 무엇을 먼저 확인해야 할지 불분명하다.
- 채팅과 상세 자료 중 어느 쪽이 중심인지 명확하지 않다.
- 현재 선택된 기업이나 테마가 무엇인지 혼란스러울 수 있다.
- 다음 질문을 직접 입력해도 되는지, 버튼을 눌러야 하는지 불분명하다.
- 상세 자료가 현재 대화와 연결되어 있는지 알기 어렵다.

이는 단순한 디자인이나 색상 문제가 아니라 **정보 위계와 상호작용 설계의 문제**이다.

# 2. 어디부터 개발 방향이 어긋났는가?

가장 큰 문제는 개별 오류가 발생할 때마다 해당 오류를 해결할 새로운 규칙과 시나리오를 추가하는 방식이 반복되었다는 점이다.

예를 들어:

1. 답변이 짧으면 더 상세하게 답변하도록 지시했다.
2. 수치가 잘못되면 숫자 검증 규칙을 강화했다.
3. 해석이 부족하면 분석 시나리오를 추가했다.
4. 근거가 부족하면 출처 검증을 추가했다.
5. 답변 실패가 발생하면 재시도 및 검증 로직을 보강했다.
6. 금융 전문 서비스 수준을 참고하며 예상 답변을 더욱 늘렸다.

그 과정에서 37개, 이후 56개에 이르는 목표 답변 시나리오까지 작성하게 되었다.

이 시나리오들은 품질 테스트 자료로서는 유용하지만, **프로그램의 기본 사용자 경험을 설계하는 일을 대신할 수는 없다.**

우리는 좋은 답변의 개별 사례를 늘리는 것과 자연스러운 대화 시스템을 만드는 것을 충분히 구분하지 못했다.

따라서 기존 시나리오는 폐기하지 않는다.

다만 앞으로는 다음처럼 역할을 변경한다.

- 사용자 흐름 설계: 프로그램이 어떤 경험을 제공해야 하는지 정의한다.
- 답변 시나리오: 각 경험이 실제로 달성되는지 검증한다.
- 금융 검증 규칙: 잘못된 수치와 근거 없는 주장을 방지한다.
- 코드 구조: 이 세 가지가 자연스럽게 작동하도록 지원한다.

**검증 규칙이나 시나리오가 사용자 경험보다 우선해서는 안 된다.**

# 3. 재정의하는 제품 목표

## 3.1 제품 정체성

이 프로그램은 금융 데이터를 보여주는 검색기가 아니다.

또한 모든 주식 질문을 해결하거나 주가를 예측하는 만능 투자 플랫폼도 아니다.

우리가 만들고자 하는 서비스는 다음과 같다.

> 사용자가 금융 시장의 테마와 기업을 자연어로 탐색하고, AI와 대화하면서 현재 상황과 주요 근거를 이해하며, 필요하면 심층 분석으로 확장할 수 있는 대화형 금융 정보 서비스.

핵심 제공 가치는 네 가지다.

1. **발견:** 사용자가 관심을 가질 만한 테마와 기업을 찾는다.
2. **이해:** 기업과 산업의 현재 상황을 쉽게 설명받는다.
3. **탐구:** 실적, 뉴스, 비교, 원인, 전망을 자유롭게 질문한다.
4. **판단 지원:** 확인된 정보로 장점·부담 요인·핵심 관찰 지점을 정리한다.

최종 매수·매도 결정을 AI가 대신하는 것이 목표는 아니다.

사용자가 스스로 판단할 수 있도록 이해와 근거를 제공하는 것이 목표다.

## 3.2 핵심 대화 원칙

**질문이 종합적인 평가를 요구한다면 결론을 먼저 설명한다.**

예:

사용자: "삼성SDI는 어때?"

적절한 방향:

- 최근 상황에 대한 핵심 평가
- 해당 평가의 중요한 실적 근거
- 실제 사업에 영향을 주는 주요 사건
- 향후 살펴볼 핵심 변수

단, 금융 수치나 뉴스는 조회·검증된 자료만 사용한다.

실제 판단에 필요한 구체적인 근거 한두 가지는 답변 본문에 포함한다.

전체 재무제표, 기사 원문, 상세 계산 자료를 채팅에 모두 나열하지 않는다.

**출처는 근거를 확인하는 수단이지, 설명을 대신하는 수단이 아니다.**

반면 "PER이 얼마야?", "매출액 알려줘"처럼 명확한 수치 조회 질문에는 해당 수치를 우선 제공한다.

모든 질문에 종합 분석 형식을 강요하지 않는다.

## 3.3 답변의 깊이는 사용자 질문에 따라 달라져야 한다

- 단순 조회 질문: 짧고 직접적으로 답한다.
- 테마 탐색 질문: 구조와 대표 기업을 이해시키는 설명을 제공한다.
- 종목 평가 질문: 종합 평가와 핵심 근거를 제공한다.
- 비교 질문: 공통 기준으로 차이를 설명한다.
- 원인 분석 질문: 실제 근거를 연결해 원인을 설명한다.
- 전망 질문: 확인된 흐름과 공개된 계획을 바탕으로 가능성과 변수를 구분한다.
- 요약 질문: 앞선 대화에서 중요한 결론만 정리한다.

답변 길이는 고정하지 않는다.

**질문에 충분히 답하는 데 필요한 만큼만 설명한다.**

# 4. 확정 사용자 흐름

## 4.1 전체 구조

기본 사용자 경험은 다음과 같다.

**자유로운 질문 시작 → 질문 의도 파악 → 필요한 자료 확인 → 직접적인 답변 → 자유로운 탐색·분석·평가 → 선택적 상세 자료 확인 → 후속 질문 또는 주제 전환 → 선택적 정리·종료·새 대화**

중요한 점은 이 과정이 일방향으로만 진행되지 않는다는 것이다.

사용자는 어느 단계에서도 이전 단계로 돌아가거나 다른 관심 대상으로 이동할 수 있다.

## 4.2 첫 화면: 자유로운 질문 진입

첫 화면은 채팅을 중심으로 구성한다.

사용자는 다음과 같이 자유롭게 시작할 수 있다.

- "요즘 관심 가질 만한 테마주 알려줘."
- "2차전지 관련주 알려줘."
- "삼성SDI 요즘 어때?"
- "두산로보틱스랑 로보티즈 비교해줘."
- "삼성전자 영업이익이 얼마나 늘었어?"
- "PER이 뭐야?"

특정 테마 선택이나 종목 선택을 반드시 거쳐야 다음 단계로 이동하는 구조는 금지한다.

추천 질문은 입력을 돕는 선택적 요소로 제공한다.

## 4.3 테마 발견

사용자:

"요즘 관심 가질 만한 테마주 알려줘."

AI는 실제 확인 가능한 최근 시장 정보와 연관성을 바탕으로 관심 테마를 소개한다.

각 테마에는 최소한 다음 정보가 있어야 한다.

- 테마명
- 관심을 받는 주요 이유
- 대표적인 사업 분야
- 관련 기업의 예시

예:

AI 반도체 / 전력 인프라 / 로봇·자동화 / 2차전지

단, 특정 테마를 실제로 '요즘 인기 있는 테마'라고 평가할 경우에는 최근 자료로 뒷받침되어야 한다.

확인할 수 없는 테마 순위나 상승 가능성을 만들어내지 않는다.

## 4.4 테마 이해와 관련 기업 탐색

사용자:

"로봇·자동화."

AI는 앞선 테마 선택 문맥을 이어받는다.

설명할 내용:

- 로봇·자동화 테마의 주요 사업 영역
- 완성 로봇, 공장 자동화, 부품·제어 등 분야별 차이
- 대표 기업과 사업상의 특징
- 추가 기업 탐색 가능성

기업 세 개만 보여주고 탐색을 종료시키지 않는다.

일정 수의 기업을 먼저 보여주더라도 필요하면 같은 테마 내 기업을 더 찾을 수 있어야 한다.

## 4.5 자유로운 대화 분기

테마를 살펴본 사용자는 다음 방향 중 원하는 곳으로 이동할 수 있다.

### A. 기업별 실적 비교

"그 기업들 실적 비교해줘."

AI는 동일한 기간과 연결·별도 기준 등을 일치시켜 기업들을 비교한다.

주요 비교 요소:

- 매출 성장성
- 영업손익
- 수익성
- 개선 또는 악화 추세
- 사업 구조에 따른 차이

단순 표 나열이 아니라 비교 결과가 무엇을 의미하는지 설명한다.

### B. 다른 관련주 탐색

"로봇 관련주 더 보여줘."

AI는 기존 기업을 불필요하게 반복하지 않고 탐색 범위를 확장한다.

사업 분야별로 정리하고, 각각 왜 로봇 테마에 속하는지 설명한다.

### C. 최근 주요 이슈

"로봇·자동화 최근 이슈 알려줘."

AI는 실제로 확인된 최신 사건을 중심으로 설명한다.

각 사건에는 다음 요소를 연결한다.

- 무엇이 발생했는가
- 어느 기업 또는 산업 분야에 관련되는가
- 어떤 의미가 있는가
- 사건 발생일과 확인 가능한 출처

동일한 사건을 다룬 여러 기사를 중복된 이슈로 제시하지 않는다.

일반적인 산업 동향과 실제 최근 발생한 사건도 구분한다.

## 4.6 개별 기업 평가

사용자:

"그중 두산로보틱스는 요즘 어때?"

AI는 기존 로봇 테마를 유지하면서 두산로보틱스를 현재 분석 대상으로 설정한다.

답변 방향:

1. 최근 사업·실적 상황에 대한 핵심 평가
2. 평가에 영향을 준 주요 실적 변화
3. 중요한 사업 및 뉴스 요인
4. 앞으로 살펴볼 핵심 변수

기업 소개를 처음부터 길게 반복하지 않는다.

필요한 사업 설명만 짧게 포함한다.

## 4.7 후속 대화

이후 사용자가 다음처럼 질문할 수 있다.

"왜 적자인데?"

"앞으로 좋아질 가능성은?"

"로보티즈와 비교하면?"

"그 회사 최근 계약은 없어?"

"그럼 지금 주가 수준은 어떤데?"

AI는 이전 문맥을 활용해 질문 대상을 파악한다.

사용자가 명확히 다른 기업을 지정하지 않았다면 기존 분석 대상을 유지한다.

단, "그 회사", "그중", "둘 중"처럼 문맥이 필요한 표현은 참조 대상을 정확히 판단해야 한다.

참조 대상이 실제로 여러 개라서 오해 가능성이 클 때에만 간결한 확인 질문을 한다.

## 4.8 대화 정리와 새로운 주제

사용자:

"지금까지 이야기한 거 정리해줘."

AI는 현재 대화에서 실제로 다룬 내용을 바탕으로 다음을 요약한다.

- 주요 결론
- 핵심 근거
- 유리한 요인과 부담 요인
- 계속 살펴볼 지표

요약은 선택 사항이다.

사용자가 요약을 요청하지 않으면 강제로 제공하지 않는다.

이후 사용자가 "이번엔 AI 반도체 알려줘"라고 말하면 새로운 관심 대상으로 전환한다.

이때 기존 로봇 관련 대화 기록을 삭제하지 않는다.

**주제 전환과 새 채팅 시작은 서로 다르다.**

새 채팅이 명시적으로 시작된 경우에만 해당 세션의 대화 문맥을 초기화한다.

# 5. 캔버스의 역할과 사용 규칙

## 5.1 역할 분리

**채팅 = 설명과 해석을 제공하는 공간**

**캔버스 = 근거와 상세 자료를 검토하는 공간**

이 구분을 UI와 코드에 일관되게 적용한다.

채팅 답변을 이해하기 위해 사용자가 반드시 캔버스를 열어야 하는 구조는 만들지 않는다.

## 5.2 캔버스를 자동으로 열 수 있는 상황

다음과 같이 사용자가 시각적 상세 자료를 명확하게 요청한 경우 자동으로 열 수 있다.

- "최근 5년 매출 차트 보여줘."
- "두 기업 재무제표를 표로 비교해줘."
- "주가 차트 보여줘."
- "분석 결과를 Excel로 만들어줘."

## 5.3 캔버스를 선택적으로 제공하는 상황

다음과 같은 일반 질문에서는 채팅이 우선이다.

- "삼성SDI는 어때?"
- "왜 실적이 나빠졌어?"
- "최근 이슈 정리해줘."
- "그 기업들 중 어디가 실적이 좋아?"

채팅에서 필요한 설명을 먼저 완료한다.

상세 비교표나 차트가 유용하다면 '상세 보기'를 제공할 수 있다.

단, 사용자가 명확하게 요청하지 않은 상황에서 매번 캔버스를 자동으로 여는 동작은 피한다.

## 5.4 캔버스 상태 관리

캔버스에는 최소한 다음 정보가 표시되어야 한다.

- 분석 기업 또는 비교 대상
- 자료 종류
- 기준 기간
- 자료 갱신 시점
- 관련 출처

사용자가 다른 기업으로 이동했다고 해서 기존 캔버스를 무조건 삭제하거나 덮어쓰지 않는다.

다만 현재 채팅의 분석 대상과 캔버스 대상이 다르다면 이를 분명히 표시한다.

캔버스에 표시된 결과와 채팅에서 설명하는 근거가 서로 다른 데이터를 가리키지 않도록 관리해야 한다.

# 6. UX/UI 전면 점검 방향

## 6.1 기존 UI를 재검토할 기준

현재 Streamlit 화면을 실제로 열어 다음을 확인한다.

- 질문 입력 영역이 가장 중요한 조작 요소로 보이는가?
- 현재 사용자와 AI의 대화 흐름이 명확하게 읽히는가?
- 종목 선택 버튼이 지나치게 많거나 중복되어 있지 않은가?
- 사용자가 자유롭게 질문할 수 있다는 사실이 드러나는가?
- 상세 표와 상태 메시지가 채팅을 방해하지 않는가?
- 현재 기업·테마·분석 기간을 쉽게 확인할 수 있는가?
- 캔버스가 어떤 대화의 결과인지 구분할 수 있는가?

## 6.2 권장 화면 구조

### 메인 채팅 영역

중심 기능:

- 사용자 질문
- AI 답변
- 핵심 근거와 출처
- 필요에 따른 후속 탐색 제안
- 텍스트 입력

메인 채팅 영역이 가장 높은 시각적 우선순위를 가져야 한다.

### 사이드 영역

필요한 보조 기능:

- 대화 기록
- 새 채팅
- 현재 관심 대상 표시
- 최소한의 탐색·설정 기능

사용 빈도가 낮은 기능을 메인 화면에 상시 노출하지 않는다.

### 상세 캔버스

필요 시 표시:

- 실적·재무제표
- 시계열 차트
- 기업 비교
- 뉴스 상세 자료
- Excel 등 결과물

상시 노출이 필요한지, 접거나 펼치는 패널이 적합한지 실제 화면 구조를 검토한다.

## 6.3 버튼 및 후속 질문 UX

답변 아래에는 맥락에 따라 0~3개 정도의 후속 탐색 방향을 제안할 수 있다.

예:

"왜 적자인가?"

"경쟁사와 비교"

"향후 전망"

단, 모든 답변에 동일한 버튼을 강제로 표시하지 않는다.

사용자가 버튼을 누르는 것과 동일한 요청을 자연어로 입력해도 같은 결과를 얻을 수 있어야 한다.

**버튼은 자유로운 대화를 대체하는 장치가 아니라 보조하는 장치다.**

## 6.4 정보 밀도 조절

일반적인 기업 질문에 전체 재무제표를 펼치지 않는다.

첫 화면에는 결론과 중요한 이유를 우선한다.

표와 차트는 많은 정보를 비교하거나 시계열 변화를 확인해야 할 때 제공한다.

불필요한 박스, 중복된 종목 선택 UI, 반복 경고문, 장식적인 그래픽을 줄인다.

'전문 금융 서비스처럼 보이는 UI'보다 **이해하기 쉽고 일관된 UI**를 우선한다.

# 7. 기존 코드의 수정 방향

**중요:** 현재 저장소의 실제 소스 코드를 확인하지 않은 상태에서 특정 파일이나 함수가 문제라고 단정하지 말 것.

아래는 수정해야 할 책임 영역이다. 실제 클래스명·파일명·의존 관계는 저장소 분석 후 결정한다.

## 7.1 먼저 전체 처리 경로를 추적할 것

사용자 질문 하나가 다음 과정을 어떻게 통과하는지 확인한다.

1. Streamlit 입력 및 세션 상태
2. 질문 의도와 대상 기업 인식
3. 대화 문맥 조합
4. 데이터 조회 계획
5. 금융 API·뉴스 조회
6. 근거 정리 및 계산
7. LLM 답변 생성
8. 사실성·숫자 검증
9. 재시도·실패 처리
10. 채팅 렌더링
11. 캔버스 생성 및 상태 업데이트

각 구간이 어떤 모듈에서 실행되는지 식별한다.

중복 처리, 불필요한 호출, 상태 충돌, 과도한 검증, 긴 대기 시간의 원인을 찾는다.

## 7.2 질문 의도 파악 단계 개선

단순 키워드 일치에 지나치게 의존하지 않도록 한다.

질문 처리 시 최소한 다음 정보를 구분해야 한다.

- 사용자의 실제 질문 목적
- 현재 관심 테마
- 현재 분석 기업
- 비교 대상 기업들
- 이전 대화에서 이어받을 대상
- 답변에 필요한 정보의 종류
- 상세 캔버스 사용 필요 여부

예:

"삼성SDI는 어때?"는 이전 문맥에 따라 기업 종합 평가일 수 있다.

"삼성SDI PER 얼마야?"는 특정 금융 지표 조회다.

"그럼 내년은?"은 앞선 기업과 분석 관점을 이어받는 후속 질문이다.

"삼성물산이 보유한 삼성전자 지분"처럼 서로 다른 역할을 하는 기업이 동시에 등장하는 문장도 정확히 처리해야 한다.

**질문에 등장하는 기업명을 무조건 모두 조회 대상으로 간주하지 않는다.**

## 7.3 대화 문맥 상태 분리

권장하는 논리적 상태는 다음과 같다.

- `active_theme`: 현재 관심 테마
- `active_company`: 현재 분석 기업
- `comparison_companies`: 비교 대상 기업들
- `last_answer_focus`: 직전 답변의 주요 논점
- `current_user_intent`: 현재 질문 의도
- `evidence_context`: 현재 답변에 사용 가능한 근거
- `canvas_result_id`: 캔버스에 연결된 상세 결과
- `conversation_id`: 현재 대화 식별자

위 이름은 설계 예시이며 기존 코드 명명 규칙에 맞춰 조정할 수 있다.

핵심은 문맥 상태와 UI 표시 상태, 금융 데이터 캐시를 무분별하게 혼합하지 않는 것이다.

## 7.4 질문별 데이터 조회 계획

현재 질문에 필요하지 않은 모든 데이터까지 조회하지 않도록 한다.

예:

"2차전지 관련주 더 알려줘."

→ 테마와 기업 관계 자료 중심

"삼성SDI는 요즘 어때?"

→ 최근 실적, 주요 사업 변화, 관련 이슈, 필요 시 주가·가치평가 자료

"영업이익 얼마야?"

→ 해당 기간의 영업이익 데이터 중심

"왜 영업이익이 줄었어?"

→ 이전 기간 실적과 주요 비용·매출 변화, 관련 사업 설명

"내년에는 어떨 것 같아?"

→ 현재 실적, 공개된 사업 계획, 확보 가능한 전망 근거

LLM이 매번 모든 도구를 호출하는 구조가 되어 있다면 개선한다.

다만 호출 수를 줄이기 위해 답변에 필요한 필수 근거까지 생략해서는 안 된다.

## 7.5 금융 데이터와 해석의 책임 분리

금융 수치는 가능한 한 구조화된 데이터로 관리한다.

수치에는 다음 속성이 보존되어야 한다.

- 기업
- 지표명
- 값과 단위
- 기준 기간
- 연결·별도 여부
- 실제 실적·잠정 실적·예상치 등 구분
- 데이터 출처와 조회 시점

증감률, 영업이익률 등의 계산은 가능한 한 결정적인 계산 로직을 사용한다.

LLM은 검증된 데이터를 바탕으로 의미를 설명하는 역할에 집중한다.

예를 들어 매출이 20% 증가하고 영업이익이 80% 증가했다면, 매출보다 이익이 더 빠르게 늘었다는 사실과 수익성 개선을 설명할 수 있어야 한다.

그 이상의 구체적인 원인을 이야기하려면 비용 구조나 사업 자료 등 관련 근거를 확인한다.

## 7.6 검증 로직은 유지하되 사용자 대화를 방해하지 않도록 개선

기존 숫자 검증과 출처 검증을 단순히 제거하지 않는다.

다음 사항을 조사한다.

- 정상적인 금융 해석을 근거 부족으로 잘못 판정하는가?
- 검증 때문에 답변의 결론이 사라지는가?
- 숫자 치환 또는 복원 과정에서 문장이 훼손되는가?
- 검증 실패 시 과도한 재생성 루프가 발생하는가?
- 검증 불합격 이유가 사용자에게 내부 문구로 노출되는가?
- 검증 실패와 데이터 조회 실패가 동일하게 처리되는가?

특히 뉴스의 사건 번호, 분기, 제품명, 기술명과 같은 숫자가 잘못 변환되지 않도록 해야 한다.

검증은 내부에서 수행하되, 사용자에게는 검증 절차 자체가 아니라 **질문에 대한 정상적인 답변**을 보여준다.

실제로 근거가 부족한 부분만 간결하게 제한한다.

## 7.7 답변 생성과 UI 렌더링 분리

LLM이 답변 문장뿐 아니라 화면의 모든 버튼·표·상태 안내까지 무분별하게 만들어내는 구조는 피한다.

가능하다면 내부적으로 다음 결과를 분리한다.

- 사용자에게 보여줄 주 답변
- 핵심 근거 및 출처
- 후속 질문 제안
- 선택적 캔버스 데이터
- 내부 검증 및 처리 상태

내부 상태나 시스템 지시 문구가 사용자 답변에 섞이지 않도록 한다.

Streamlit 재실행 시 같은 응답이 두 번 표시되는 문제도 함께 조사한다.

각 사용자 턴에 대해 최종 답변이 한 번만 확정·렌더링되도록 관리한다.

## 7.8 응답 속도 개선

기존의 약 1분 응답 사례는 반드시 조사한다.

단계별 처리 시간을 기록할 것.

- 질문 해석
- 데이터 조회
- 뉴스 수집
- LLM 생성
- 검증
- 재시도
- UI 업데이트

이 기록으로 실제 병목을 구분한다.

검토할 개선 방향:

- 중복 조회 제거
- 재사용 가능한 데이터 캐싱
- 독립적인 데이터 호출의 병렬 처리
- 불필요한 전체 데이터 조회 제거
- 재시도 횟수 및 조건 개선
- 짧은 조회 질문과 심층 분석의 처리 경로 구분

목표는 모든 답변을 무조건 짧게 만드는 것이 아니다.

**답변의 실제 가치에 비해 대기 시간이 과도하지 않도록 만드는 것**이다.

## 7.9 자료 부족과 오류 처리

다음 세 상황을 구별한다.

**A. 자료가 공개되지 않은 경우**

공개된 최신 자료를 기반으로 답할 수 있는 부분까지 설명한다.

**B. 자료 조회가 실패한 경우**

해당 자료를 불러오지 못했다고 짧게 안내하고, 사용 가능한 다른 근거가 있으면 활용한다.

**C. 근거가 서로 충돌하는 경우**

출처와 기준 시점을 확인하고, 확정할 수 있는 사실과 차이가 있는 수치를 구분한다.

이 경우에도 모든 답변을 "판단할 수 없습니다"로 종료하는 구조는 피한다.

# 8. 작업 순서: 전면 수정이 아닌 단계별 재설계

## PHASE 0 — 현행 시스템 진단

**코드 변경 전에 반드시 수행한다.**

조사 대상:

- 전체 프로젝트 구조
- 질문 입력부터 출력까지의 실행 경로
- 문맥 및 세션 상태 관리
- 금융 데이터 호출 구조
- LLM 프롬프트와 검증 체계
- 캔버스 연결 구조
- 실제 병목과 반복 호출
- 기존 테스트 및 예상 시나리오

산출물:

1. 현재 아키텍처 요약
2. 사용자 경험상의 문제와 연결된 코드 영역
3. 문제별 실제 확인 근거
4. 유지할 기능과 수정할 기능
5. 불필요하거나 중복된 로직
6. 단계별 수정 계획

이 단계에서는 원인이 확인되지 않은 부분을 추측으로 확정하지 않는다.

## PHASE 1 — 대화 문맥과 질문 의도 개선

우선적으로 해결할 문제:

- 모호한 종목 질문의 잘못된 해석
- 이전 대화 맥락 상실
- 기업 전환 시 대상 혼동
- 직접 조회와 종합 분석의 구분 실패
- 일반적인 후속 질문의 거부

이 단계의 목표는 **사용자가 무엇을 물었는지 제대로 이해하는 것**이다.

## PHASE 2 — 답변 품질 구조 개선

개선 항목:

- 질문에 대한 직접적인 답변
- 종합 평가가 필요한 경우 결론 우선
- 필요한 금융 수치만 선정
- 숫자와 의미의 연결
- 뉴스 사건과 사업 영향의 연결
- 불필요한 원문·재무자료 나열 제거
- 과도한 경고·면책성 문구 제거
- 출처와 분석 내용의 일치

기존 답변 시나리오는 참고 자료로 사용하되 모든 예시를 고정된 출력 형식으로 구현하지 않는다.

## PHASE 3 — UI/UX 재설계

개선 항목:

- 메인 채팅 중심 화면
- 종목 선택 영역 단순화
- 자유 입력과 선택형 탐색의 공존
- 후속 질문 버튼의 선택적 제공
- 캔버스의 선택적 개방
- 현재 분석 대상 표시
- 캔버스와 채팅 문맥의 일관성
- 중복 상태 표시와 불필요한 정보 제거

개발 과정에서는 실제 Streamlit 화면을 기준으로 점검한다.

가능하다면 사용자 질문부터 종목 탐색까지의 전체 흐름을 직접 재현하며 수정한다.

## PHASE 4 — 안정성 및 성능 개선

개선 항목:

- 내부 프롬프트 노출 방지
- 중복 답변 출력 방지
- 숫자 검증의 오탐지 감소
- 데이터 조회 실패 처리
- 복잡한 질문의 재시도 흐름
- 응답 대기 시간 개선
- 캔버스 결과의 정확한 연결

이 단계의 목표는 정상적인 대화가 예외 처리 때문에 중단되지 않도록 하는 것이다.

## PHASE 5 — 실제 사용자 대화 검증

독립적인 한 문장 테스트만 하지 않는다.

**처음 질문부터 후속 대화와 새로운 주제 전환까지 이어지는 전체 대화**를 테스트한다.

검증 시나리오는 다음을 포함한다.

### 테스트 A: 테마 발견과 확장

"요즘 관심 가질 만한 테마주 알려줘."

→ "로봇·자동화."

→ "관련주 더 보여줘."

→ "이 회사들은 서로 뭐가 달라?"

기대 결과:

- 테마별 이유를 설명한다.
- 기업의 사업 차이를 설명한다.
- 탐색 범위를 자연스럽게 확장한다.
- 기존 질문을 불필요하게 반복하지 않는다.

### 테스트 B: 비교에서 개별 기업 분석으로

"로봇 기업들 실적 비교해줘."

→ "그중 두산로보틱스는 어때?"

→ "왜 적자인데?"

→ "그럼 앞으로 좋아질 가능성은?"

기대 결과:

- 비교 대상을 유지한다.
- 특정 기업으로 자연스럽게 초점을 전환한다.
- 실적과 사업 근거를 연결한다.
- 근거 있는 전망과 추정의 범위를 구분한다.

### 테스트 C: 자유로운 종목 질문

"삼성SDI는 요즘 어때?"

→ "LG에너지솔루션과 비교해줘."

→ "그럼 PER은 어디가 더 높아?"

→ "그 차이는 왜 생긴 거야?"

기대 결과:

- 첫 질문에 종합적으로 답한다.
- 후속 질문에서 비교 대상을 유지한다.
- PER의 값만이 아니라 의미를 설명한다.
- 근거 없는 상대 평가를 만들지 않는다.

### 테스트 D: 주제 변경과 재탐색

"2차전지 관련주 알려줘."

→ "삼성SDI는 어때?"

→ "이번엔 AI 반도체 관련주 알려줘."

→ "그중 SK하이닉스는 어떤데?"

기대 결과:

- 새 주제에 맞게 대화가 전환된다.
- 이전 2차전지 자료가 새 기업 분석에 섞이지 않는다.
- 이전 대화 기록은 유지된다.

### 테스트 E: 자료 부족과 오류

다음 상황을 각각 재현한다.

- 특정 기간의 미발표 실적
- 금융 API 오류
- 뉴스 조회 결과 없음
- 서로 다른 출처의 수치 불일치
- 근거는 충분하지만 검증기가 답변을 거부하는 상황

기대 결과:

- 실제 오류 원인에 맞게 처리한다.
- 사용할 수 있는 근거까지 버리지 않는다.
- 내부 검증 문구를 그대로 노출하지 않는다.
- 질문과 무관한 고정 실패 메시지로 종료하지 않는다.

### 테스트 F: 캔버스와 UI

"두 기업 실적을 표로 보여줘."

→ 캔버스 열기

→ 다른 기업에 대해 질문

→ 기존 비교표 다시 확인

→ 새 채팅 시작

기대 결과:

- 캔버스의 대상과 기간이 표시된다.
- 채팅 내용과 캔버스 결과가 잘못 연결되지 않는다.
- 이전 결과를 다시 확인할 수 있다.
- 새 채팅에서 과거 문맥이 의도치 않게 섞이지 않는다.

# 9. 완료 기준

수정 완료는 단순히 단위 테스트가 통과했다는 이유만으로 선언하지 않는다.

다음 항목을 기준으로 실제 대화 품질을 평가한다.

| 평가 영역 | 완료 기준 |
|---|---|
| 질문 이해 | 사용자의 의도와 문맥에 맞는 답변 제공 |
| 테마 탐색 | 기업 나열을 넘어 관련성과 차이 설명 |
| 종목 평가 | 종합 질문에 실질적인 종합 평가 제공 |
| 금융 해석 | 수치와 그 의미가 자연스럽게 연결됨 |
| 뉴스 분석 | 실제 사건·날짜·기업 영향·출처가 연결됨 |
| 후속 대화 | 기업·테마·논점을 잃지 않고 계속 대화 |
| 주제 전환 | 다른 기업이나 테마로 자연스럽게 이동 |
| 답변 완결성 | 추가 질문 없이도 현재 질문의 핵심을 이해 |
| 자료 검증 | 근거 없는 수치와 허위 출처를 생성하지 않음 |
| 오류 처리 | 정상 질문을 불필요하게 거부하지 않음 |
| UI | 사용자의 현재 행동과 다음 선택이 명확함 |
| 캔버스 | 필요할 때만 사용하고 자료 문맥을 유지 |
| 안정성 | 내부 지시 노출·중복 응답·상태 충돌 방지 |
| 성능 | 실제 병목을 측정하고 불필요한 대기 감소 |

모든 테스트에서 다음도 함께 확인한다.

**"사용자가 답변을 읽고 실제로 이해했는가?"**

이 기준을 기존의 기능 실행 성공 여부와 별도로 평가해야 한다.

# 10. Codex에게 요구하는 구체적인 수행 방식

이번 작업은 기존 프로젝트의 성격을 바꾸는 중요한 재정렬 작업이다.

따라서 다음 원칙을 따라 진행한다.

## 첫째, 즉시 대규모 코드를 수정하지 말 것

먼저 현재 프로젝트가 어떻게 동작하는지 조사하고, 문제와 연결된 실제 코드 경로를 식별한다.

문제가 있다고 추정되는 이유만으로 모듈을 삭제하거나 아키텍처를 전면 교체하지 않는다.

## 둘째, 기존 기능을 가능한 한 보존할 것

이미 구현된 테마 검색, 재무 조회, 뉴스 수집, 숫자 검증, Excel, 캔버스를 재사용한다.

기존 기능을 재작성해야 한다면 그 필요성과 영향을 먼저 설명한다.

## 셋째, 하나의 수정보다 전체 사용자 경험을 기준으로 판단할 것

예를 들어 "삼성SDI는 어때?"라는 답변 하나가 개선되었다고 해서 작업이 끝난 것은 아니다.

그 뒤 "왜?", "다른 기업과 비교하면?", "그럼 내년은?"이라고 질문해도 자연스럽게 작동해야 한다.

## 넷째, 프롬프트 추가만으로 구조 문제를 해결하려 하지 말 것

답변 문제의 원인이 질문 라우팅, 데이터 조회, 상태 관리, 검증 로직, 렌더링이라면 해당 코드 영역을 수정한다.

프롬프트 개선이 필요한 경우에만 프롬프트를 조정한다.

## 다섯째, 검증 체계를 무력화하지 말 것

정확한 수치와 출처를 유지하는 것은 중요하다.

다만 과도한 검증으로 정상적인 해석까지 제거하는 구조도 개선해야 한다.

목표는 검증을 없애는 것이 아니라 **정확성과 자연스러운 답변을 동시에 달성하는 것**이다.

## 여섯째, 사용자에게 개발 내부 사정을 노출하지 말 것

사용자 답변에 프롬프트, placeholder, 내부 Fact ID, 검증 실패 사유, 디버그 상태가 나타나서는 안 된다.

개발자 로그와 사용자에게 보이는 문장을 철저히 분리한다.

## 일곱째, 단계별 변경 내용과 실제 검증 결과를 보고할 것

각 작업 단계마다 다음을 간결하게 보고한다.

- 발견한 실제 문제
- 문제의 원인과 근거
- 수정한 코드 영역
- 기존 기능에 미칠 영향
- 수행한 테스트
- 개선된 점과 아직 남은 문제

검증하지 않은 품질 개선을 완료했다고 보고하지 않는다.

# 11. 우선순위

**P0 — 서비스 신뢰성 회복**

- 내부 프롬프트 노출
- 중복 응답
- 정상 후속 질문의 비정상 종료
- 데이터·문맥 혼동
- 잘못된 수치 또는 출처 연결

**P1 — 대화의 핵심 경험 완성**

- 문맥 기반 질문 이해
- 테마 및 기업 탐색
- 종합 평가
- 금융 데이터의 의미 설명
- 후속 대화 연결

**P2 — UI/UX 구조 정리**

- 채팅 중심 화면
- 자연스러운 종목 탐색
- 후속 질문 인터페이스
- 선택적 캔버스
- 현재 분석 대상과 상세 자료 표시

**P3 — 성능·품질 개선**

- 데이터 호출 최적화
- LLM 처리 시간
- 검증 오탐지 개선
- 뉴스 품질 개선
- 응답 길이 및 표현 최적화

**P4 — 고급 기능 확장**

- 심화 어닝콜 분석
- 복잡한 전망·컨센서스 비교
- 고급 가치평가
- 광범위한 산업별 특화 분석

P4는 P0~P3의 기본 사용자 경험이 충분히 완성된 뒤 검토한다.

# 12. 첫 번째로 제출해야 할 결과물

이 문서를 받자마자 모든 단계의 개발을 일괄 실행하지 말 것.

**첫 번째 수행 목표는 현행 코드에 대한 진단과 실제 수정 계획의 확정이다.**

먼저 다음 결과를 제출한다.

### 1. 현재 프로그램 동작 분석

질문 입력부터 최종 채팅·캔버스 출력까지 실제 실행 경로를 정리한다.

### 2. 기존 사용자 경험을 방해하는 문제 식별

현재 프로그램이 왜 단순 조회 결과처럼 느껴지는지 실제 코드 구조와 연관 지어 설명한다.

### 3. 수정 대상 코드 목록

수정이 필요한 파일·함수·모듈과 수정 이유를 명시한다.

단, 아직 코드를 확인하지 않은 상태에서 파일을 추정해 작성하지 않는다.

### 4. UX/UI 변경안

현재 화면을 기준으로 유지·이동·통합·제거할 UI 요소를 정리한다.

새로운 사용자 흐름에 따른 화면 상태도 제안한다.

### 5. 단계별 실제 구현 계획

P0~P3 작업을 기존 구조에 맞게 세분화하고, 각 단계의 검증 방법과 회귀 위험을 제시한다.

# 최종 지시

앞으로 개발의 기준 질문은 다음과 같아야 한다.

**"이 수정이 사용자에게 더 자연스럽고 유용한 금융 대화를 제공하는가?"**

단순히 더 많은 수치를 조회하거나, 더 많은 검증 규칙을 적용하거나, 더 많은 버튼과 상세 화면을 제공한다고 해서 좋은 금융 챗봇이 되는 것은 아니다.

사용자는 금융 시스템의 내부 복잡성을 이해할 필요가 없다.

사용자는 관심 있는 테마나 기업을 질문하고, AI가 중요한 자료를 확인해 현재 상황을 설명해 주며, 궁금한 부분을 계속 물어볼 수 있기를 기대한다.

따라서 이번 프로젝트의 최종 목표는 다음 한 문장으로 정리한다.

> **정확한 금융 정보를 바탕으로, 사용자가 기업과 시장을 이해하고 자연스럽게 탐색할 수 있는 대화형 금융 AI를 완성한다.**

이 목표를 최우선 기준으로 삼아 현재 코드와 UX/UI를 단계적으로 재설계하라.
