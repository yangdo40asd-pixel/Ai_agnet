## 1. 이 프로젝트가 만들려는 것

사용자가 “반도체”처럼 관심 테마를 입력하면 국내 상장 종목 후보를 제안하고, 대표 종목의 조회 가능한 금융 정보와 관련 뉴스 제목을 모아 AI 리포트로 보여주는 웹 서비스다. 사용자가 여러 곳에서 종목·금융·뉴스 정보를 따로 찾고 연결하는 부담을 줄이는 것이 목적이다.

기획서 기준의 기본 처리 흐름은 다음과 같다.

~~~text
테마 입력
  → 관련 종목 후보 3개 제안
  → 대표 종목의 상장 여부·종목코드 확인
  → 주가·PER 및 관련 뉴스 조회
  → 수집한 정보로 AI 리포트 생성
  → 지표·설명·출처·조회 시각·누락 상태 표시
~~~

초기 분석 대상은 후보 목록의 첫 번째 종목이다. 후보 순서는 시장 대표성이나 투자 우선순위를 뜻하지 않는다. AI는 제공된 데이터 범위에서 설명해야 하며, 매수·매도 추천을 만드는 것이 목표는 아니다. 현재 뉴스 분석 입력은 기사 본문이 아니라 제목이다.

현재 서비스 실행 코드는 별도 데이터베이스나 독립적인 웹 API 서버를 사용하지 않는다. Streamlit 애플리케이션 안에서 Python 코드가 외부 데이터 서비스와 AI 서비스를 직접 호출한다. 따라서 앞으로의 “모듈 분리”는 우선 Python 파일 사이의 책임 분리를 뜻하며, 별도 서버나 데이터베이스 구축을 필수 작업으로 간주하지 않는다.

예전 [PROJECT_PLAN.md](../계획/PROJECT_PLAN.md)에는 OpenAI 우선, PBR·ROE·DART 등 여러 후보 기능이 적혀 있다. 현재 app.py는 Groq 모델을 직접 호출하고 주가·PER와 뉴스 제목을 사용한다. 계획 문서나 설치된 패키지 목록보다 현재 코드와 최종 기획서에서 확정한 범위를 우선해야 한다.

## 3. 현재 코드에서 실제로 이어지는 과정

1. Streamlit의 텍스트 입력창과 “분석 시작” 버튼으로 테마를 받는다. 입력값이 완전히 빈 문자열이면 경고를 표시한다.
2. Groq 모델을 호출해 종목명 3개를 쉼표 구분 문자열로 받으려 한다.
3. 문자열의 첫 번째 항목을 대표 종목으로 삼는다. 응답 형식·종목명·상장 여부를 충분히 검증하지 않는다.
4. FinanceDataReader의 KRX 목록에서 대표 종목명과 정확히 일치하는 행을 찾아 종목코드를 얻는다.
5. yfinance에 종목코드와 고정 접미사 .KS를 붙여 currentPrice와 trailingPE를 조회한다. 시장 구분별 변환과 누락값 표시는 완성되지 않았다.
6. NAVER API에 “테마 + 대표 종목”으로 뉴스 3건을 요청한다. 현재 정렬값은 sim이며, AI에는 정제한 제목 문자열만 전달한다.
7. 수집한 값과 뉴스 제목을 다시 Groq 모델에 넘겨 네 부분의 마크다운 리포트를 요청한다.
8. 생성된 텍스트를 그대로 화면에 출력한다. 외부 호출 중 예외가 나면 일반 오류 메시지를 표시한다.

이 연결은 과거 PoC의 핵심 성과다. 다만 이번 점검에서는 외부 API를 실제 호출해 최신 성공 여부를 확인하지 않았다. “코드가 있다”, “과거에 시연했다”, “현재도 정상 응답한다”는 서로 다른 상태로 기록해야 한다.

## 4. 목표와 현재 상태의 차이

| 기능 | 현재 확인된 상태 | 앞으로 채워야 할 부분 |
|---|---|---|
| 테마 입력 | 입력창·버튼·로딩 표시 있음 | 공백만 입력한 경우, 재입력 안내, 화면 상태 정리 |
| 대화형 화면 | 실제 app.py는 일반 입력창과 마크다운 결과 | 기획한 대화형 입력·결과 화면으로 구성할지 확정하고 구현 |
| 후보 3개 제안 | AI 문자열을 쉼표로 나눔 | 형식 검증, 중복 제거, 빈 응답 처리, 후보 수 확인 |
| 대표 종목 선택 | 첫 후보 자동 사용 | 첫 후보가 불일치할 때의 안내·재입력 규칙 확정 |
| 상장 종목 확인 | KRX 종목명 완전 일치 검색 | 종목명 표기 차이, 동명이인, 검색 실패 상태 처리 |
| 시장별 티커 | 모든 종목코드에 .KS 사용 | KRX 시장 구분을 이용한 티커 변환 검증 |
| 금융 지표 | currentPrice·trailingPE 조회 코드 있음 | 값 누락, None, 단위, 기준 시점, 출처 표시 |
| 관련 뉴스 | 제목 최대 3건 수집 | 링크·발행 시각·출처 보관, 0건 처리, 정렬 기준 확인 |
| AI 리포트 | 네 항목을 프롬프트로 요청 | 형식·수치 일치 검사, 근거 없는 내용 차단, 누락 시 문장 조정 |
| 결과 근거 | 현재 화면에는 원문 링크·조회 시각이 없음 | 지표 출처·뉴스 원문·조회 시각을 화면과 결과에 표시 |
| 오류 처리 | 전체를 하나의 try/except로 감쌈 | 입력·종목·금융·뉴스·AI 오류를 구분해 안내 |
| 모듈 구조 | 기능이 app.py에 집중됨 | data, agents, ui 파일로 분리하고 한 형식으로 연결 |
| 통합 검증 | 과거 수동 PoC 기록과 진단 스크립트 있음 | 정상·누락·실패 사례를 재현하며 결과를 대조 |
| 최종 시연 | 계획 문서와 예상 화면은 있음 | 실제 구현 화면·검증 결과·시연 절차 갱신 |

특히 현재 코드에서 AI 응답이 비정상이어도 첫 후보를 그대로 사용한다. 후보가 KRX에서 발견되지 않으면 주가와 PER은 “알 수 없음”으로 남지만 뉴스 조회와 리포트 작성은 계속될 수 있다. “정보 없음” 같은 문구 뒤에 “원”을 붙여 표시할 가능성도 있다. 뉴스 요청에는 명시적인 제한 시간이 없고, 현재 정렬값 sim을 사용하므로 뉴스가 항상 최신순이라고 설명할 수 없다. AI가 작성한 수치와 실제 조회값을 비교하는 코드도 없다.

## 5. 앞으로의 개발 순서와 완료 기준

아래 순서는 작업 의존관계를 따른다. 예상 날짜나 주차는 아직 확정하지 않는다.

### 1단계. 기본 범위와 데이터 전달 형식 확정

- 입력: 테마 문자열. 앞뒤 공백 제거, 빈 입력, 지나치게 긴 입력을 어떻게 다룰지 결정한다.
- 종목 후보: 후보명, 검증된 종목명, 종목코드, 시장 구분, 검증 상태를 구분한다.
- 금융 데이터: 조회값, 단위, 자료 출처, 조회 시각, 누락 사유를 담는다.
- 뉴스 데이터: 제목, 원문 링크, 발행 시각, 제공 출처를 담는다. 실제 응답에서 확보 가능한 필드를 먼저 확인한다.
- 오류 상태: 입력 오류, 종목 미확인, 금융값 누락, 뉴스 0건, 외부 요청 실패, AI 응답 실패를 구분한다.
- 대표 종목 규칙: 초기 버전은 첫 후보를 분석한다. 후보가 확인되지 않으면 다른 종목을 임의로 끼워 넣지 않고 사용자에게 상태를 알린다.

완료 기준: 데이터 수집 부분의 출력과 AI·화면 부분의 입력이 한 문서에 정의되고, 정상·누락·실패 예시가 각각 있다.

### 2단계. 외부 연동을 다시 확인

- 가상환경에서 현재 AI, KRX 목록, yfinance, NAVER API의 단독 응답을 재확인한다.
- 각 응답의 필드 이름·자료 시점·누락 사례와 오류 형태를 기록한다.
- API 키 값은 기록·화면·저장소에 노출하지 않는다.
- 현재 고정된 AI 모델을 계속 사용할지 응답 품질·속도·이용 조건을 확인해 결정한다.
- 결과 기록에 실행일을 남겨 예전 PoC 성공과 현재 검증을 구분한다.

완료 기준: 네 외부 연동에 대해 성공 또는 실패 원인, 확인한 시각, 실제 응답 필드를 기록한다. 패키지 설치 확인만으로 이 단계를 완료 처리하지 않는다.

### 3단계. 종목·금융 데이터 기능 구현

- src/data/stock.py 등에 KRX 종목 목록 조회, 후보명 확인, 종목코드 및 시장 구분, 금융 정보 조회를 분리한다.
- 종목명 완전 일치가 실패할 때의 처리 규칙을 만든다. AI가 만든 후보를 검증 없이 상장 종목으로 표시하지 않는다.
- 시장 구분별 yfinance 티커 변환을 확인한다. 현재의 .KS 고정 처리를 검토한다.
- 주가·PER가 없거나 None인 경우를 정상 수치와 구분한다. “정보 없음원” 같은 표시를 막는다.
- 금융 정보의 출처와 조회 시각을 함께 반환한다. “실시간 주가”라는 표현은 실제 데이터의 시점이 확인된 경우에만 사용한다.

완료 기준: 유효 종목, 확인되지 않는 종목, 시장이 다른 종목, PER 누락 사례에서 각각 예측 가능한 결과 또는 오류 상태를 반환한다.

### 4단계. 뉴스 수집 기능 구현

- src/data/news.py 등에 NAVER API 호출과 응답 정제를 분리한다.
- 검색 결과의 제목 외에 원문 링크·발행 시각·출처를 확보하고, HTML 태그와 문자 엔터티를 올바르게 정리한다.
- 최신 뉴스가 목표인지 관련도가 높은 뉴스가 목표인지 정한 뒤 정렬 기준과 화면 표현을 일치시킨다. 현재 코드는 sim 정렬이다.
- 요청 제한 시간, 비정상 응답, 뉴스 0건, 일부 필드 누락 상태를 처리한다.
- 기사 본문을 수집하지 않는다면 AI 입력과 화면에서 “제목 기반”이라는 범위를 지킨다.

완료 기준: 정상 뉴스, 0건, API 오류 응답을 구분하며 사용자가 원문으로 이동할 수 있다.

### 5단계. AI 후보 제안·리포트 생성 기능 분리

- src/agents/report.py 등에 후보 제안과 리포트 생성을 별도 함수로 만든다.
- 후보 제안의 출력 형식을 정하고 파싱·중복·빈값을 검사한다. 현재의 쉼표 분리만으로는 결과를 보장할 수 없다.
- 검증된 종목·금융·뉴스 데이터만 리포트 입력으로 전달한다.
- 리포트의 네 항목, 한국어 문체, 숫자·단위 표기와 누락값 표기 규칙을 정한다.
- AI가 제공되지 않은 기사 본문, 수치, 사실을 덧붙이거나 매수·매도 판단을 단정하지 않도록 출력 결과를 점검한다.
- AI 결과에 적힌 종목명·주가·PER가 전달한 데이터와 일치하는지 확인한다. 프롬프트 지시만으로 검증을 대신하지 않는다.

완료 기준: 같은 입력 형식에서 결과 항목이 일관되고, 수치 불일치·근거 없는 값·빈 AI 응답이 검출된다.

### 6단계. 실제 서비스 화면과 상태 표시

- src/ui/app.py는 입력, 진행 상태, 결과, 안내 메시지 표시를 맡도록 정리한다.
- 기획서의 화면 설계에 맞춰 종목 후보, 대표 종목 지표, 관련 뉴스, AI 설명을 구분해 보여준다.
- 출처·조회 시각·누락 상태를 결과에서 바로 확인할 수 있게 한다.
- 빈 입력, 종목 미확인, 일부 금융값 누락, 뉴스 0건, 외부 요청 실패를 사용자에게 서로 다르게 설명한다.
- 실제 채팅 화면이 필요하다면 현재 입력창을 대화형 UI로 바꾼다. poc_archive/poc_app.py의 채팅 화면은 더미 응답이므로 그대로 완성 화면으로 보지 않는다.
- 결과가 생성되지 않았을 때 “분석 완료” 메시지가 나타나지 않도록 한다.

완료 기준: 한 번의 테마 입력으로 전체 흐름을 볼 수 있고, 사용자가 어떤 값이 실제로 조회됐으며 무엇이 누락됐는지 알 수 있다.

### 7단계. 통합 검증과 오류 재현

- 정상 입력 여러 개로 종목 후보부터 결과 표시까지 실행한다.
- 공백 입력, AI 후보 형식 오류, 상장 종목 미확인, 시장별 코드, 주가·PER 누락, 뉴스 0건, API 제한·시간 초과, AI 실패를 확인한다.
- 화면에 적힌 숫자와 출처를 원자료·응답 기록과 대조한다.
- 서로 다른 테마에서도 리포트 형식이 유지되는지 본다.
- 응답 시간을 측정하되 코드에 적힌 “약 10~15초”를 실제 측정 없이 보장하지 않는다.
- 반복 가능한 핵심 검증은 작은 자동 테스트로 남기고, 비용이나 변동성이 있는 실제 API 호출은 별도의 수동 점검으로 기록한다.

완료 기준: 정상 흐름과 주요 예외 사례의 실제 결과·판정·수정 사항이 남아 있고, 동일 오류를 다시 재현할 수 있다.

### 8단계. 실행 안내·기획서·시연 자료 정리

- 프로젝트 실행 방법, 필요한 환경변수 이름, 사용 중인 핵심 패키지를 README에 정리한다.
- .env.example의 설명을 실제 사용 코드와 맞춘다. 현재 예시 파일은 OpenAI 키를 “필수”라고 적지만 app.py는 Groq 키를 사용한다.
- 설치된 패키지 21개를 모두 “사용한 기술”로 쓰지 않는다. 현재 서비스에서 직접 사용하는 것과 향후 선택 기능을 구분한다.
- 기획서의 예상 화면·시스템 구조·WBS 완료 표시를 실제 구현 결과와 맞춘다.
- 시연용 테마, 예상 결과, 데이터 누락 시 보여줄 안내, API 실패 시 대처 절차를 기록한다.
- 민감한 키 값이 문서·스크린샷·Git에 포함되지 않았는지 확인한다.

완료 기준: 새로운 사람이 실행 안내만 보고 앱을 실행할 수 있고, 기획서의 완료 주장과 실제 화면이 일치한다.

## 6. 핵심 범위 이후의 확장 기능

다음은 기본 흐름을 먼저 안정화한 뒤 검토할 기능이다. 패키지가 설치돼 있거나 과거 계획 문서에 등장한다는 이유로 현재 완료 또는 필수 구현으로 표시하지 않는다.

| 확장 항목 | 현재 상태 | 먼저 필요한 조건 |
|---|---|---|
| 후보 종목 선택·비교 | 첫 후보만 분석 | 기본 종목 검증과 결과 형식 안정화 |
| DART 재무제표, PBR·ROE 등 추가 지표 | 키와 패키지는 있으나 현재 서비스 코드에 연동되지 않음 | 출처·시점·지표 의미와 누락 처리 확정 |
| 주가·재무 차트 | plotly 설치, 현재 서비스 화면에서는 미사용 | 신뢰할 조회 기간과 데이터 형식 |
| 리포트 PDF 내려받기 | reportlab 설치, 기능 없음 | 화면 리포트·출처 표시 완성 |
| Gemini·OpenAI 등 모델 교체 | 연동용 패키지·설정 이름 일부 존재, 현재 서비스는 Groq 호출 | 모델 선택 기준과 출력 검증 |
| 캐시·데이터베이스·별도 서버 | 현재 구조에 없음 | 반복 조회나 기록 보관의 필요성 확인 |
| Selenium·비동기 요청·멀티 에이전트 | 관련 패키지 일부 설치, 현재 서비스에서는 미사용 | 실제 기능상 필요성 확인 |

## 7. 가장 먼저 시작할 작업

1. 현재 외부 연동을 각각 다시 실행하고 성공·실패·응답 필드를 기록한다.
2. 종목·금융·뉴스가 반환할 공통 데이터 형식과 누락·오류 상태를 확정한다.
3. 종목 후보 검증과 시장별 티커 처리를 먼저 구현한다.
4. 금융·뉴스 모듈을 분리하고 출처·조회 시각을 결과에 담는다.
5. AI 리포트와 화면을 새 데이터 형식에 연결한 뒤 정상·예외 사례를 검증한다.

현재 단계의 정확한 표현은 “핵심 흐름을 한 파일로 연결한 PoC”다. 완성 여부는 모듈 파일의 존재만으로 판단하지 않고, 실제 데이터 검증·근거 표시·오류 처리·통합 실행 결과까지 확인해 판단한다.
